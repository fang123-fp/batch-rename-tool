# 本地后端服务部署说明

## 目标

- 把 PDF 识别统一放到一台固定电脑执行
- 减少不同客户端浏览器版本带来的兼容性差异
- 提升扫描证书批量识别的稳定性
- 让局域网内其他电脑只负责上传和查看结果

## 适用场景

适合：

- 业务主要是扫描版 PDF
- 现场电脑有 Win7 / 老版 Chrome
- 你希望所有识别逻辑固定跑在一台更稳定的电脑上
- 想保留当前网页交互，但不再把 OCR 压在每个客户端浏览器上

## 架构说明

当前工具分成两层：

1. 前端页面
- 负责上传文件
- 展示自动识别结果
- 允许人工修改字段
- 生成重命名 ZIP

2. 本地后端服务
- 提供 `/api/health`
- 提供 `/api/extract`
- 在服务端本机启动受控 Chrome 工作页
- 统一执行 PDF 提取和 OCR
- 把字段结果返回前端页面

因此：

- 访问页面的客户端浏览器可以比较旧
- 真正影响识别稳定性的，只剩下服务端那台电脑的环境

## 环境要求

- Node.js 18+
- Chrome / Edge 桌面版
- 建议把这套工具放到一台长期在线、性能更稳定的电脑上

## 安装步骤

### 1. 复制项目目录到目标电脑

整份目录都要带上，尤其不要漏掉：

- `vendor/`
- `docs/`
- `server.js`
- `app.js`
- `index.html`
- `package.json`

### 2. 安装依赖

```bash
npm install
```

### 3. 启动服务

```bash
npm start
```

或：

- macOS 双击 `start_lan_server.command`
- Windows 双击 `start_lan_server.bat`

### 4. 打开浏览器访问

- 本机访问：`http://localhost:8123`
- 局域网访问：`http://服务端电脑IP:8123`

## 运行机制

页面打开后：

- 普通文本文件继续在前端直接读取
- PDF 文件优先发给 `/api/extract`
- 后端在本机受控 Chrome 中完成识别
- 前端收到结构化结果后回填表格

如果后端暂时不可用：

- 页面会自动回退到前端本地识别
- 但这时稳定性会再次依赖访问者自己的浏览器环境

## 为什么这种方式更稳

相比纯前端模式，它有几个关键优势：

- 浏览器环境固定，不再受每个用户机器差异影响
- 老版 Chrome 只负责传文件和看结果，不再承担核心 OCR
- 后端统一串行调度 PDF 识别，更容易控制状态
- 同一次“从内容重新读取”由服务端完整跑完后一次性回传，减少前端局部状态互相覆盖

## 已做的稳定性处理

- PDF 默认只读取第一页
- 证书样本优先启用第一页锁定模式
- 本地后端工作页会显式关闭递归调用，避免后端再调用自己
- 重新读取前会先清空旧一轮提取产物，避免旧状态残留污染新结果
- 手动修改过的字段不会被自动结果强行覆盖

## 端口与网络

默认端口：

- `8123`

可改：

```bash
PORT=8137 npm start
```

如果局域网内其他电脑访问不到：

- 检查服务端电脑防火墙
- 检查两台电脑是否在同一网段
- 用 `http://服务端电脑IP:端口` 访问，不要用 `localhost`

## 浏览器路径问题

后端会自动尝试查找：

- Google Chrome
- Microsoft Edge
- Chromium

如果都没找到，可以手动指定：

```bash
PUPPETEER_EXECUTABLE_PATH=/你的浏览器可执行文件路径 npm start
```

## 当前边界

这次改动已经能显著提升稳定性，但要明确边界：

- 如果 PDF 本身扫描质量极差，OCR 仍然可能有误差
- 想做到业务意义上的“100% 无错”，最终仍需要人工复核或更强的后端 OCR / 模型服务
- GitHub Pages 这类纯静态托管无法承载本地后端模式

## 推荐部署方式

如果你后续要在另一台电脑长期跑，推荐：

1. 选一台固定电脑作为识别服务机
2. 安装 Node.js 和 Chrome
3. 把项目目录完整拷过去
4. 先执行一次 `npm install`
5. 用 `npm start` 长期开着
6. 让其他人通过局域网地址访问

这样以后就不是“每个用户的浏览器都在识别”，而是“统一由服务机识别”。
