# V2 优化文档

## 目标

- 在现有“上传文件 -> 识别 -> 下载 ZIP”之外，新增“本地目录模式”
- 在不牺牲当前证书字段精准度的前提下，继续优化本地后端读取速度
- 把后续优化拆成可以直接排期执行的实现方案，而不是只停留在方向描述

## 背景

当前版本已经解决了两类核心问题：

- 兼容性问题：Win7 / 老版 Chrome 不再直接承担核心 PDF OCR
- 稳定性问题：证书第一页锁定模式、本地后端统一识别、重读状态隔离已经基本成型

但还有两个用户价值没有完全解决：

1. 现在只能导出 ZIP，不能直接改源文件名
2. 当前本地后端更稳，但同机使用时不一定更快

## 当前基线

基于 2026-06-11 的同机实测，当前后端模式比前端直读更慢，主要是固定开销偏大：

- 单文件 `页面提取自－SCAN0002-2.pdf`
  - 后端模式：约 `7.2s`
  - 前端直读：约 `4.7s`
- 三文件 `SCAN0002-2/3/4`
  - 后端模式：约 `13.4s`
  - 前端直读：约 `12.1s`

这说明当前后端的优势主要是“统一环境、稳定一致”，不是“天然更快”。

## V2 范围

### In Scope

- 新增本地目录模式
- 新增原地重命名能力
- 增加回滚和重命名清单
- 优化后端读取链路，减少固定开销
- 为批量扫描 PDF 提供更快的后端路径

### Out of Scope

- 不在 V2 中直接接入云 OCR / 第三方模型服务
- 不在 V2 中做用户权限系统
- 不在 V2 中支持“远程客户端直接改自己本机文件”
- 不在 V2 中重写整套前端 UI 风格

## 一、改成本地目录模式实现方案

## 1.1 业务目标

让用户可以：

1. 选择一个待处理目录
2. 让后端直接扫描该目录中的文件
3. 自动提取字段并预览新文件名
4. 点击确认后，直接修改源文件文件名
5. 出错时可以回滚

## 1.2 关键边界

这部分必须先写清楚，否则后面一定会误解：

- 目录模式只能操作“服务端电脑本地目录”或“服务端可访问的网络共享目录”
- 如果页面开在 A 电脑，但后端服务跑在 B 电脑，那么目录模式改的是 B 电脑能访问到的目录，不是 A 电脑本地磁盘
- 如果希望改客户端自己电脑上的原文件名，必须是：
  - 页面和后端都运行在同一台电脑
  - 或者文件放在后端电脑挂载到的共享目录里

## 1.3 推荐的 V2 目录模式定义

V2 采用：

- `上传模式`：继续保留，适合临时使用、跨设备使用、导出 ZIP
- `本地目录模式`：新增，适合固定服务机、本地操作员、直接改源文件名

不建议 V2 直接删除上传模式，两个模式并存最稳。

## 1.4 推荐用户流程

### 模式一：上传模式

- 现有流程保持不变

### 模式二：本地目录模式

1. 切换到“本地目录模式”
2. 选择目录来源：
   - 手动输入目录路径
   - 从最近目录选择
   - 同机部署时可调用服务端原生目录选择器
3. 点击“扫描目录”
4. 后端返回文件列表和初始识别结果
5. 页面展示：
   - 原文件名
   - 识别字段
   - 预览新文件名
   - 冲突/缺失/失败状态
6. 用户手动修正少量字段
7. 点击“确认原地重命名”
8. 后端执行两阶段重命名
9. 页面展示结果，并提供回滚按钮

## 1.5 架构方案

### 前端

新增状态：

- `mode = upload | local-directory`
- `directoryTaskId`
- `directoryPath`
- `directoryRecords`
- `renameTransaction`
- `canRollback`

新增界面区块：

- 模式切换
- 目录路径输入区
- 扫描目录按钮
- 最近目录列表
- 原地重命名确认弹层
- 回滚入口

### 后端

新增接口建议：

1. `POST /api/directories/pick`
- 作用：同机部署时调起系统目录选择器
- 说明：只作为可选增强，不作为唯一入口

2. `POST /api/directories/scan`
- 输入：
  - `directoryPath`
  - `fields`
  - `scanOptions`
- 输出：
  - `taskId`
  - `files`
  - `warnings`

3. `POST /api/directories/refresh`
- 作用：对已扫描目录重新提取字段

4. `POST /api/rename/preview`
- 输入：
  - `taskId`
  - `template`
  - `fieldOverrides`
- 输出：
  - `previewRows`
  - `conflicts`
  - `invalidNames`

5. `POST /api/rename/commit`
- 输入：
  - `taskId`
  - `confirmedRows`
- 输出：
  - `renameManifestPath`
  - `renamedCount`
  - `failedCount`
  - `rollbackToken`

6. `POST /api/rename/rollback`
- 输入：
  - `rollbackToken`
- 输出：
  - `restoredCount`
  - `failedCount`

## 1.6 服务端目录选择实现建议

目录选择分两层：

### 必选方案

- 页面允许直接输入服务端目录路径
- 后端校验路径是否存在、是否可读、是否在允许范围内

### 可选增强

同机部署时增加系统选择器：

- macOS：`osascript` 调系统选目录
- Windows：PowerShell + `FolderBrowserDialog`

这样做的原因：

- 浏览器自身无法替服务端机器打开原生目录选择器
- 但本地 Node 后端可以调用系统层能力

## 1.7 原地重命名核心算法

V2 必须采用“两阶段重命名”，不能直接逐个改正式名字。

### 阶段 1：临时名过渡

把所有待改文件先重命名为唯一临时名，例如：

- `.rename-tmp-<taskId>-0001.pdf`
- `.rename-tmp-<taskId>-0002.pdf`

目的：

- 避免 A 改成 B 时，B 还没腾出来
- 避免重名冲突和覆盖

### 阶段 2：临时名改正式名

临时名全部成功后，再统一改成目标名。

### 失败回滚

如果阶段 2 某一步失败：

- 立即停止后续改名
- 用事务日志把已改过的文件回滚

## 1.8 必须落盘的事务清单

每次原地重命名都必须生成一份 manifest，例如：

- `rename-task-20260611-103000.json`

至少包含：

- `taskId`
- `createdAt`
- `directoryPath`
- `template`
- `fields`
- `originalPath`
- `tempPath`
- `finalPath`
- `status`
- `rollbackToken`

这样即使页面关闭，也还能补做回滚或问题排查。

## 1.9 冲突与异常处理规则

### 重名冲突

V2 建议默认规则：

- 先在预览阶段报出冲突
- 默认自动追加 `(2) / (3)` 后缀
- 但允许用户关闭自动后缀，改成“冲突即阻止提交”

### 非法文件名

统一清理：

- Windows 非法字符：`\\ / : * ? \" < > |`
- 首尾空格
- 保留系统不允许的保留名处理

### 权限错误

如果文件不可写：

- 标记为失败
- 不影响其它文件预览
- 提交时整体阻止或分批跳过，按最终产品取舍决定

### 文件被占用

如果目标文件被其他程序占用：

- 返回明确错误
- manifest 中记录失败原因

## 1.10 安全与权限边界

目录模式比上传模式风险更高，V2 需要明确约束：

- 默认只允许访问配置白名单内的目录
- 可选：默认只允许当前工作根目录下的子目录
- 如果允许任意路径，至少需要二次确认
- 局域网共享部署时，目录模式建议只对可信操作者开放

## 1.11 V2 目录模式实施拆分

### D1：目录扫描基础版

- 增加模式切换
- 增加目录路径输入
- 后端扫描目录并回传文件列表
- 页面展示识别结果

### D2：预览与提交

- 加入预览文件名
- 加入冲突检测
- 加入原地重命名提交

### D3：回滚与审计

- 增加 manifest
- 增加 rollback 接口
- 增加页面回滚入口

## 1.12 目录模式验收口径

- 用户可在页面切换到本地目录模式
- 后端能扫描目标目录并返回识别结果
- 页面能预览最终文件名
- 点击确认后，源文件名被直接修改
- 若中途失败，可用 manifest 完成回滚
- 上传模式原有能力不回归

## 二、优化后端读取速度的具体落实方案

## 2.1 当前后端为什么会慢

当前后端链路是：

1. 页面把文件发给 `/api/extract`
2. Node 后端先把文件落到临时目录
3. 后端再启动一个受控 Chrome 工作页
4. 工作页再次把这些临时文件当“上传文件”喂回现有页面逻辑
5. 页面逻辑完成提取后，再通过诊断快照把结果返回后端

因此当前慢在这几个点：

1. 每批都要有一次 HTTP 往返
2. 文件要走一次“上传 -> 落盘 -> 再上传”
3. 每批都要 `newPage + goto + 初始化工作页`
4. 正常识别路径也会构建完整诊断快照
5. OCR 仍然是串行队列
6. 后端本质上还是在“浏览器里跑前端逻辑”，不是原生后端提取链

## 2.2 V2 后端提速原则

- 先减少固定开销
- 再减少重复搬运
- 再把“无需 OCR 的 PDF”从浏览器工作页里剥离出来
- 最后才考虑提高 OCR 并发

## 2.3 速度优化分阶段方案

### S1：低风险降开销

这是第一阶段，优先做，风险低、见效快。

#### S1-1 复用常驻工作页

当前问题：

- 每次 `/api/extract` 都 `browser.newPage()`
- 每次都 `page.goto(workerUrl)`
- 每次都重置整页状态

改法：

- 启动服务时创建一个常驻 `workerPage`
- 后续批量识别只做“清空记录 -> 注入本批文件 -> 开始识别”
- 只在异常时重建页面

预期收益：

- 降低单批固定启动开销
- 对单文件和小批量最明显

#### S1-2 `/api/health` 改成启动后缓存

当前问题：

- 每次前端批处理前都会先调用一次健康检查

改法：

- 页面首次加载或首次识别时检查一次
- 成功后缓存状态
- 后续直接尝试 `/api/extract`
- 只有失败时再触发健康检查或重连

预期收益：

- 少一次无效请求

#### S1-3 正常路径不再返回完整诊断快照

当前问题：

- 正常识别时也通过 `buildDiagnosticsSnapshot()` 把大对象整体取回

改法：

- 新增轻量结果导出函数，例如 `buildExtractionPayload()`
- 默认只返回：
  - `values`
  - `autoValues`
  - `contentState`
  - `contentMessage`
  - `documentProfile`
- 只有用户主动点击“导出诊断信息”或指定 `diagnostics=true` 时，才生成完整诊断数据

预期收益：

- 降低工作页和后端之间的大对象序列化成本

#### S1-4 后端文件接收改成以内存为主

当前问题：

- 现在 `multer.diskStorage` 先把文件写盘，再从磁盘喂给工作页

改法：

- 改为 `multer.memoryStorage`
- 小文件直接走内存
- 大文件可保留阈值回退到临时文件

预期收益：

- 减少小批量场景的磁盘 I/O

### S2：消除“后端再上传一次文件”

这是第二阶段，性价比很高。

当前问题：

- 后端收到文件后，又通过 `input.uploadFile(...)` 把文件重新喂给工作页

改法：

- 不再依赖临时文件路径
- 后端直接把文件 buffer/base64 送到工作页
- 工作页里构造 `File` 对象后直接调用现有 `addFiles(...)`
- 这样链路变成：
  - `页面 -> Node 内存 -> workerPage File对象`

预期收益：

- 去掉一次落盘
- 去掉一次二次文件上传
- 对单文件和小批量速度改善明显

### S3：把“PDF 第一页文字直提取”迁到 Node 后端原生执行

这是第三阶段，属于收益最大的中期方案。

当前问题：

- 现在哪怕 PDF 本身就有可提取文字，也还是进浏览器工作页

改法：

- 后端直接用 Node 侧 PDF 引擎做第一页文字提取
- 先跑“非 OCR 快速路径”
- 只有以下情况才转工作页 OCR：
  - 文字层为空
  - 关键字段仍然缺失
  - 文档被识别为扫描版

建议做法：

- 提取逻辑仍然沿用当前第一页规则
- 先把字段判定函数抽成纯函数模块
- Node 和前端共用同一套字段评分逻辑

预期收益：

- 对“文本型 PDF”提速最大
- 对“部分字段缺失但不是纯扫描件”的 PDF 也能减少 OCR 触发

### S4：把字段规则抽成共享核心模块

这是第四阶段，是后续长期演进的地基。

改法：

- 新建共享模块，例如：
  - `shared/extraction-core.js`
- 把这些能力搬进去：
  - 字段别名
  - 字段候选打分
  - 证书模板锁定字段判断
  - 证书编号 / 管理编号 / 厂商 / 客户名称等规则

然后：

- 前端继续复用
- Node 后端直接调用

收益：

- 后端以后不需要继续“开浏览器页才能跑规则”
- 让 S3 之后的真正后端化成为可能

### S5：有限并发 OCR 池

这是第五阶段，必须慎重做。

当前问题：

- OCR 现在完全串行

改法：

- 仅对“需要 OCR 的文件”建立有限并发 worker 池
- 默认建议并发不是越大越好
- 推荐初始值：
  - `1`：最稳
  - `2`：V2 推荐默认
  - `3`：只在 CPU 足够、样本回归稳定后再开放

原则：

- 文本提取与规则判定可以并行
- OCR 并发只在扫描版且批量较大时启用

预期收益：

- 对 10 份以上批量扫描件收益明显
- 对单文件收益不大

## 2.4 不牺牲精准度的约束条件

后端提速必须遵守这些红线：

- 证书第一页锁定模式不能取消
- 当前字段判定规则不能因为提速被弱化
- 手动修正过的字段不能被重新覆盖
- 只读第一页的默认策略继续保留
- 诊断信息能力不能被彻底删掉，只能按需生成

## 2.5 建议实施顺序

推荐按下面顺序做，不建议跳步：

1. `S1` 常驻工作页 + health 缓存 + 轻量返回
2. `S2` 去掉临时文件二次上传
3. `D1` 本地目录模式基础版
4. `S3` Node 原生第一页文字提取
5. `D2` 原地重命名预览与提交
6. `S4` 共享字段规则核心
7. `S5` 有限并发 OCR 池
8. `D3` 回滚与审计

原因：

- 先把速度上的低风险收益吃掉
- 再开始做目录模式
- 共享核心模块和 OCR 池放到中后期，风险更好控

## 2.6 V2 预期效果

以下是目标，不是硬性承诺：

### 单文件 / 小批量

通过 `S1 + S2`，目标是：

- 后端模式单文件耗时较当前下降 `20% ~ 35%`
- 小批量 `1~5` 份文件的固定开销明显下降

### 文本型 PDF

通过 `S3`，目标是：

- 文本型 PDF 不再进 OCR 工作页
- 速度较当前后端模式下降 `40% ~ 70%`

### 批量扫描件

通过 `S5`，目标是：

- 在 4 核以上服务机上，10 份以上扫描件批量识别时间再下降 `20% ~ 50%`

## 结论

V2 的核心不是简单“再改快一点”，而是把产品从“上传后导出 ZIP 的识别工具”升级为：

- 既能上传导出
- 又能直接扫描本地目录
- 还能原地重命名
- 并且后端识别链逐步从“浏览器套浏览器”过渡到“真正的本地后端提取”

如果按本文档执行，后续优化的主线应该是：

1. 先减固定开销
2. 再做目录模式
3. 再把后端真正后端化
